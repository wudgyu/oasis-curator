# Oasis Curator（绿洲馆长）产品手册

> 版本：v1.0　适用对象：团队管理员、平台使用者、部署运维人员

## 1. 产品概述

Oasis Curator 是一款面向团队的私有化部署 AI 文档平台，核心理念可以概括为一句口号：知识有归，脉络可循，疑问可解。产品灵感来自电影《头号玩家》中博物馆管理员 Ogden Morrow 的虚拟身份 "The Curator"——他不争不抢，却总能在关键时刻递上最对的那把钥匙。Oasis Curator 扮演的正是这样一位数字馆长：守护知识完整性，梳理信息脉络，引导用户抵达真正需要的答案。

平台不是搜索引擎，也不是简单的问答机器人，而是一位懂行的策展人。它围绕企业文档全生命周期，提供文档上传、智能解析、语义检索、RAG 问答、Agent 自动化处理等能力，并深度结合多租户管理与 RBAC 权限体系，确保每一份知识都在正确的权限边界内流动。

平台采用前后端分离架构：前端基于 Vue 3 与 Element Plus 构建，后端基于 FastAPI 与 SQLAlchemy 实现，向量检索层使用 ChromaDB，LLM 层支持 DeepSeek、Kimi 等云端模型以及 Ollama 本地模型双模式。整个系统通过 Docker Compose 编排，一条命令即可完成部署。

## 2. 快速开始

部署前请准备：一台 Linux 服务器（推荐 4 核 16G 内存），已安装 Docker 与 Docker Compose。云端模式还需要 DeepSeek 或 Kimi 的 API Key 以及智谱 Embedding API Key。

云端模式启动步骤：第一步，复制环境变量模板 .env.example 为 .env，填入 API Key；第二步，执行 docker compose -f docker-compose.cloud.yml up -d；第三步，浏览器访问前端地址，使用初始管理员账号登录；第四步，在文档管理页上传第一份文档，等待解析与向量化完成，即可在问答页提问。

离线模式启动步骤：第一步，运行下载脚本获取 Qwen 2.5 7B 与 BGE-large-zh-v1.5 模型权重；第二步，将环境变量 DEPLOY_MODE 修改为 offline；第三步，执行 docker compose -f docker-compose.offline.yml up -d。离线模式不需要任何 API Key，全部推理在本机完成。

首次登录后建议立即完成三件事：修改初始管理员密码；创建业务租户与角色；上传团队核心文档建立知识库基线。

## 3. 核心特性总览

Oasis Curator 包含六大核心能力。第一，多租户认证授权基础设施：支持多租户管理、RBAC 2.0 权限模型、JWT 认证与 API Key 管理，是平台的统一底座。第二，RAG 文档问答：从文档解析、向量化、检索到生成的全链路实现，回答附带引用溯源，检索不到的答案明确拒答而不是编造。第三，文档处理 Agent：基于 Function Calling，由 LLM 自主编排解析、翻译、摘要、入库等文档处理步骤。第四，RAG 质量保障 Agent：采用检索、生成、验证、融合四个 Agent 协作的方式，逐句校对答案，防止幻觉。第五，IAM 配置生成器：管理员用自然语言描述权限需求，系统自动生成符合 RBAC 2.0 模型的权限配置 JSON。第六，MCP 文档服务：将文档检索与问答能力封装为标准 MCP 工具，供外部 AI Agent 生态接入。

平台还支持云端与离线双模式部署。云端模式使用 DeepSeek、Kimi 等在线大模型与智谱 Embedding API；离线模式完全本地化，使用 Ollama 运行 Qwen 2.5 模型、BGE-large-zh-v1.5 做向量化，适用于内网隔离环境与信创场景。

## 4. 多租户与认证授权

平台以租户为数据隔离的基本单位。每个租户拥有独立的用户体系、角色体系与文档空间，租户之间的数据在数据库层、向量库层均严格隔离，互不可见。

用户角色分为三类：admin（管理员）可以管理本租户用户、角色与全部文档；editor（编辑）可以上传和管理文档；viewer（只读）只能查看和提问。角色权限通过 RBAC 2.0 模型管理，支持数据范围（data scope）维度，例如某个只读角色可以只被授权访问特定组织树下的文档。

认证采用 JWT 机制：用户登录后获得有效期 24 小时的令牌，令牌载荷中包含用户 ID、租户 ID 与角色编码。后端所有受保护接口校验令牌并强制以令牌中的租户 ID 过滤数据，即使请求参数被篡改，也无法越权访问其他租户的数据。文档检索与问答接口同样携带租户上下文，向量检索时通过元数据过滤确保租户 A 上传的文档永远不会被租户 B 检索到。

## 5. 文档上传与向量化

文档入库流程分为五步：上传、解析、切分、向量化、入库。支持 PDF、TXT、Markdown 三种格式，其中 PDF 解析基于 pdfplumber 逐页提取文本，TXT 与 Markdown 自动识别 UTF-8 与 GBK 编码。

文档切分提供两种策略。固定字符数切分：按 500 字符一个窗口滑动切分，相邻窗口重叠 100 字符，避免关键信息被切在边界上。按段落切分：以空行为段落边界，短段落自动合并，使每个文本块稳定在 500 到 800 字符之间，超长段落按句号、问号等句边界继续拆分。每个文本块都记录来源文件名、段序号与页码，用于问答时的引用溯源。

向量化默认使用智谱 embedding-2 模型，输出 1024 维向量；本地验证模式可使用 MiniLM 轻量模型。向量与元数据（文件名、段序号、页码、租户 ID、文档 ID）一起存入 ChromaDB。平台在 ChromaDB 中使用独立数据库命名空间 oasis，collection 内的每条向量都带有租户标识元数据，检索时强制执行租户过滤。

一个完整的上传入库示例：上传一份 12 页的 PDF 产品手册，系统逐页提取约九千字符，按段落策略切分出 18 个文本块，每块平均 550 字符，随后分三批调用 Embedding 接口完成向量化，最后连同元数据写入向量库。整个过程通常在三十秒内完成，前端展示解析进度与最终块数量。

## 6. RAG 文档问答

问答链路是平台的核心场景。用户提问后，系统先将问题向量化，在向量库中检索最相似的 5 个文本块（Top-5），再调用 LLM 对这 5 个候选块逐一打分（1 到 10 分），取分数最高的 3 个作为最终上下文（Top-3），这一步称为重排序，能够显著过滤掉向量相似度虽高但语义不相关的干扰块。

随后系统将 Top-3 文本块与用户问题拼接为提示词，提示词模板明确约束模型：根据参考资料回答问题；如果资料中没有答案，必须明确说不知道。生成回答时要求模型在每个事实后标注来源，格式为 [来源: 文件名, 第N段]，用户可以据此回溯原文核对。

拒答机制是平台对抗幻觉的关键设计。当文档库中确实没有相关信息时，模型会回答"抱歉，当前文档库中没有相关信息"，而不是凭借通用知识编造答案。这是企业知识库场景与通用聊天场景最本质的区别。

以产品手册为例：用户提问"RAG 问答的重排序保留几个候选块"，系统检索到手册第 6 节内容，回答"重排序后取 Top-3，即分数最高的 3 个文本块"，并标注来源。若用户提问"平台支持哪些数据库的 SQL 方言"，手册中没有相关内容，系统检索到的文本块相似度均低于阈值，回答"抱歉，当前文档库中没有相关信息"。

## 7. 文档处理 Agent

文档处理 Agent 基于 Function Calling 实现，LLM 自主决定调用哪些工具、按什么顺序执行。Agent 内置五个工具：parse_document 解析文档提取文本与表格；extract_tables 按页码范围提取表格数据；translate_text 完成中英互译；summarize_text 生成指定长度的摘要；index_chunks 将处理后的文本块向量化入库。

典型场景包括：用户说"上传这份英文 PDF 并入库"，Agent 执行 parse_document、translate_text、index_chunks 三步；用户说"总结这份文档的核心内容"，Agent 执行 parse_document 后调用 summarize_text；用户说"这份报告有表格，提取出来并翻译成中文"，Agent 依次执行 parse_document、extract_tables、translate_text。工具调用结果回传给 LLM，LLM 可以继续调用下一个工具或生成最终回复，前端展示每一步的执行过程而非黑盒等待。当模型不支持 Tool Call 时，系统自动降级为 Prompt 注入方式完成同样的编排。

## 8. RAG 质量保障 Agent

质量保障 Agent 是平台防幻觉的核心方案，采用四个 Agent 协作：检索 Agent 负责向量检索 Top-5；生成 Agent 基于检索结果生成带引用的回答；验证 Agent 逐句比对回答与原文，输出每句的验证结论；融合 Agent 综合生成结果与验证结果输出最终答案。

工作流中，验证 Agent 若发现某句不被原文支撑，工作流回到生成 Agent 重新生成，最多循环三轮。三轮后仍未通过验证的，标记为低置信度。最终答案分三级置信度输出：高置信度直接呈现；中置信度呈现但标注"以下内容可能不准确"；低置信度明确告知用户"文档中未找到相关信息"。每个 Agent 的输出都记录在状态中，用户可回溯完整决策链。

与单次 RAG 相比，质量保障管线在标准评测集上的幻觉率显著降低：验证 Agent 能够在答案输出前拦截大部分无依据的陈述，将"看似合理但原文未提及"的内容挡在最终答案之外。

## 9. IAM 配置生成器

IAM 配置生成器将权限管理经验与 LLM 结合：管理员用自然语言描述权限需求，系统生成符合 RBAC 2.0 模型的权限配置 JSON。例如输入"创建一个只读角色，只能看北京机房和上海机房的云主机资源"，系统输出包含角色定义、资源权限列表、数据范围三部分的 JSON 配置。

生成过程内置 Schema 校验：LLM 输出先经过 Pydantic 模型校验，不合法则自动重试，最多两次。系统预设了全局只读、部门管理员、审计员等常见权限模板，用户说"我要全局只读"即可直接匹配模板。生成的角色绑定当前租户，不同租户可以有同名角色互不冲突；与同租户已有角色重名时，系统提示冲突并询问是否覆盖。

## 10. MCP 文档服务

平台通过 MCP（Model Context Protocol）协议将文档能力标准化输出，任何兼容 MCP 的 Agent 客户端都可以接入。服务注册了三个工具：search_documents 执行语义检索，返回相关文本块及来源；ask_document 执行完整的 RAG 问答，返回带引用的答案；list_documents 列出当前租户可访问的文档清单。

每个工具都有明确的 JSON Schema 定义，MCP 调用时携带租户标识，数据隔离规则与平台内部一致。在 Claude Desktop 等 MCP 客户端中配置服务地址后，即可在对话中直接查询企业文档库。MCP 的设计理念与传统的 OpenAPI 开放平台一脉相承：定义标准化的接口契约，让调用方自动发现和调用，只是调用方从第三方系统变成了 AI Agent。

## 11. 部署模式

云端模式面向公网可达环境：LLM 使用 DeepSeek 或 Kimi API，Embedding 使用智谱 embedding-2，向量库使用 ChromaDB。通过环境变量配置各服务的 API Key，支持多模型路由与自动降级——当默认模型不可用时自动切换到备用模型，降级链顺序为 DeepSeek、Kimi、Ark。

离线模式面向内网隔离环境与信创场景：LLM 使用 Ollama 运行 Qwen 2.5 7B 模型，Embedding 使用本地 BGE-large-zh-v1.5 模型，全部推理在本机完成，不依赖任何外部网络。切换部署模式只需修改环境变量 DEPLOY_MODE 为 offline，系统自动加载本地模型配置。

两种模式均通过 Docker Compose 一键部署：云端使用 docker-compose.cloud.yml，离线使用 docker-compose.offline.yml。离线部署前运行下载脚本获取模型权重，模型文件随部署包一同分发，适用于完全断网的私有化交付场景。

硬件建议：云端模式最低配置 2 核 4G 内存；离线模式推荐 8 核 32G 内存并建议配备一块不少于 24G 显存的 GPU，纯 CPU 推理时 Qwen 2.5 7B 的生成速度约为每秒 8 到 12 个字符，问答体验会有明显等待。

## 12. API 概览

认证相关：POST /api/auth/login 登录获取令牌；POST /api/auth/logout 登出；GET /api/auth/me 获取当前用户信息。租户与用户管理：GET /api/tenants、POST /api/tenants 等接口支持分页查询与租户增删改；用户接口按当前租户过滤。文档相关：POST /api/documents 上传文档并自动完成解析、切分、向量化入库；GET /api/documents 分页列出本租户文档；DELETE /api/documents/{id} 删除文档及其向量；GET /api/documents/search 语义检索文本块。问答相关：POST /api/qa/ask 提交问题并返回带引用的答案。IAM 相关：POST /api/iam/generate-role 自然语言生成权限配置；POST /api/iam/save-role 保存角色。所有接口统一返回格式 {code, message, data}，非法参数返回 422 并附带具体字段错误信息，未登录访问受保护接口返回 401。

## 13. 常见问题

问：向量库为什么选择 ChromaDB？答：ChromaDB 内嵌部署、持久化简单，元数据过滤天然支持租户隔离，适合团队规模的知识库场景；对超大规模数据可以考虑迁移 Milvus。

问：chunk 切分参数如何调优？答：固定字符数切分默认 500 字符、重叠 100 字符；段落切分目标区间 500 到 800 字符。检索质量不理想时，优先调整切分粒度而不是检索数量。

问：切换 Embedding 模型后旧文档还能检索吗？答：不同 Embedding 模型输出的向量维度与语义空间不同，切换模型后需要重建向量索引，重新导入文档。

问：离线模式与云端模式的效果差异？答：离线模式使用的 Qwen 2.5 7B 与 BGE-large-zh-v1.5 均为开源模型，效果略逊于云端大模型，但完全本地化，适用于保密要求高的环境。

问：拒答机制会不会误伤正常提问？答：拒答只发生在检索到的文本块确实不包含答案时。提问方式影响很大：问题表述越接近文档中的术语，检索命中率越高。平台的重排序环节专门缓解了向量检索误召回的问题。

问：文档删除后向量会立即消失吗？答：会的。删除文档时系统同时删除数据库中记录与向量库中该文档的全部向量，保证数据一致性，避免出现"文档已删但答案还能检索到"的幽灵数据。
